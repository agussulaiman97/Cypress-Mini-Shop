I organized Cypress Mini Shop as a small React app in src/ with Cypress specs grouped by user journey under cypress/e2e/auth and cypress/e2e/dashboard. Shared cy.login() and cy.addProduct() commands keep repeated actions consistent, and both commands are exercised across multiple spec files. This structure separates app code, fixtures, reusable commands, and focused tests.

The fixture-based login test reads user.json, while a separate test gets testEmail and testPassword from cypress.config.js through Cypress.env(). The login command uses cy.session() to cache the demo authentication state. Dashboard tests use cy.intercept() to stub the product list and observe product creation. They verify names, SKUs, prices, stock counts, inventory totals, and the add-product request and response. The new product test submits Cypress Canvas Tote (BAG-204, $19.95, 12 units).

To reproduce flakiness, the product-list response is delayed by 500 ms. An immediate row assertion could run before the UI updates. I fixed that race by waiting for the intercepted response and using retryable .should() checks instead of fixed sleeps. I ran all four specs in parallel, with two Cypress runners at a time. Seven tests passed, none failed or were skipped, and the merged Mochawesome report captures outcomes and durations. The deterministic stubs and network-based waits made results repeatable while the report gives reviewers a quick view of what each flow verified.
